> 上一課看到，No-Code／Low-Code 讓業務人員也能做出自動化流程。但「快」和「簡單」是有代價的。這一課是導入評估時最常考的：**它的優勢在哪、會卡在哪，以及人人都能做 App 之後要怎麼管**。

## 優勢：快、門檻低、大家一起做

- **開發快**：現成的元件和連接器，幾週就能上線，不必等資訊部門排程。
- **門檻低**：視覺化介面讓業務人員也能參與（常稱為「公民開發者」），資訊部門可以專注在核心系統。
- **治理有工具**：多數平台內建**角色權限、資料存取控管與操作紀錄**，有助於落實資料治理。

<Callout type="trap">
  「內建權限管理」<strong>不等於</strong>「自動符合所有資安與個資規範」。業務人員做的應用，上線前仍然需要安全審查。
</Callout>

## 限制：四種常見的「卡關」

| 限制 | 什麼情況 | 例子 |
|---|---|---|
| 🔒 **供應商鎖定** | 資料用專有格式、匯出受限、沒有 API | 想換平台時，資料和功能都搬不走 |
| 🧩 **客製化不足** | 只能用平台提供的元件 | 獨家排程演算法、要串接自訂 AI 模型 |
| 🐢 **效能與環境限制** | 通用框架多一層封裝；部署環境有差異 | 毫秒級交易；邊緣裝置資源不足；多雲部署不支援 |
| 🔌 **整合能力** | 平台能不能接上既有系統 | 選型時要確認 **API、Webhook、開放架構** |

<Callout type="key" title="選平台時要確認的事">
  不要只比開發速度。還要確認：<strong>資料能不能匯出、有沒有標準 API 與 Webhook、支不支援公司的部署環境（多雲、地端、邊緣），以及能不能符合資安與法規要求</strong>。做儀表板時，最該優先確認的是<strong>資料串接是否穩定、能否即時更新</strong>。
</Callout>

## 人人都能做 App 之後：治理與測試

**AI 民主化**讓各部門都能自己做應用，但沒有規範時很容易失控：功能重複的系統一堆、資料欄位定義不一致、沒審核就上線、權限一團亂。解法不是禁止，而是建立：

- **統一的開發與上線管理機制**：誰可以做、做完誰來審、怎麼上線。
- **共用標準**：資料欄位定義、可重複使用的元件、AI 模型的使用規範。
- **權限與稽核**：善用平台內建的角色權限與存取紀錄。

**測試**也不能只靠「點點看能不能用」。跨系統的流程要建立**可重複執行的自動化測試**，並用**模擬的外部服務**（服務虛擬化）來測試各種情況，例如外部系統斷線或回傳錯誤時，流程會不會出問題。

<Callout type="note" title="Vibe Coding 也一樣">
  第 2 課的 Vibe Coding 和 Low-Code 一樣能快速做出原型。差別在於：Vibe Coding 生成的是<strong>可自由修改的程式碼</strong>，彈性高，但品質很依賴提示詞，上線前一定要審查與測試；Low-Code 則受平台元件限制，但比較一致、好管理。
</Callout>

## 常見誤區

<Misconception claim="用 Low-Code 平台做的系統，就不需要測試和維護">
  <strong>不對。</strong>跨系統串接一樣會出錯，仍需要自動化測試、監控與維護。
</Misconception>

<Misconception claim="平台有內建權限管理，所以各部門做的應用都會自動合規">
  <strong>不對。</strong>工具能幫忙，但規範、審核與稽核仍要有人負責。
</Misconception>

<Misconception claim="業務一成長，No-Code 平台也能無限擴充">
  <strong>不一定。</strong>新創公司常在初期用 No-Code 快速上線，但業務成長後，可能因為平台不支援自訂模型或擴充功能而卡關。導入前就要想好之後怎麼轉移。
</Misconception>
